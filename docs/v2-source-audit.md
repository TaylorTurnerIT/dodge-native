# Source decisions before vectorization and PPO

This record reconciles the read-only Opus audit of `d7ad951` with the [supplied v2 specification](SPEC_PRIVILEGED_VIT_RL.md). The raw result is retained in `learning/runs/v2-orchestration/opus_v2_review-result.json`. It is a review of the original source, not a verdict on the active Milestone 1 implementation.

## Confirmed corrections and required checks

- **Use raw score changes on every executed frame.** `collision_check` continues after a lethal collision, so a pickup can also score on that frame. Count the score delta, apply the death penalty once, and exclude that frame's alive bonus. Test this interaction explicitly.
- **Score source behavior is richer than the prose examples.** Each resolved enemy death gives 0.5, so a pair can yield 1.0. Explode iterates a mutating enemy list and scores per visited entry, including powerups and explosions. Use actual fixed-point deltas rather than reconstructing score from event counts. Report raw score and display/ceil score separately.
- **Static rectangles can fade.** A rectangle with `sh < 2` is not necessarily charging. Decreasing visible `sh` must not predict a future lethal phase. Derive phase and displacement/growth from observed raw-frame history; do not consult queued targets or waits.
- **History must be measured at raw-frame cadence.** Rectangle centers/extents should be compared against the immediately preceding raw frame inside action repeat, with active-pattern/index lifecycle handling. The same history principle applies to growth and shrinking explosions. Do not expose hidden `max_size`, `life`, future targets, or scheduling counters as policy features.
- **Separate termination and truncation.** Freeze the episode cap, return the actual final observation, bootstrap PPO on time-limit truncation, and stop on death. No Game Over image enters the visual stack.
- **Keep the action/mode contract strict.** Policy actions are the nine existing directions; menu O/X masks are internal startup inputs. A decision step must begin in `Mode::Game`. Startup is one X frame plus twelve neutral frames on the current engine; implement a bounded loop to Game and verify its observed count.
- **Do not turn invisible schedules into entity tokens.** Pattern 23 contains a zero-area offscreen rectangle used for spawn control. A raw active-pattern flag or raw catalog token can leak this state. Token activity and pattern activity must reflect visible/inferable geometry, with explicit fixtures for this pattern.
- **Treat rectangle overflow as a contract failure.** The proposed cap of 16 needs a catalog/dynamic sweep and empirical baseline evidence. Enemy overflow must have deterministic selection and a logged counter. Never silently truncate long lethal walls.
- **Parity needs active gameplay coverage.** The required 100 × 2,000 random-frame comparison is supplemented by targeted powerup, death, pattern, transition, and collision-disabled fixture coverage. Report coverage counters; idle terminal frames do not establish pattern parity.
- **Match baseline and environment behavior.** Before PPO, run deterministic policies through the original-engine baseline harness and the vectorized environment on matching seeds/configuration/caps. Compare per-episode raw score, survival, and terminal reason exactly.
- **Evaluate both gate configurations.** Initial Milestone 0 measures difficulty 2. Before the teacher gate, establish matching difficulty-3 baselines and a difficulty-1/no-pattern curriculum sanity check. Freeze the score/survival gate from those measurements; the spec's two-times-score example is not an observed threshold.

## Parent qualifications to the review

**RNG scheduling.** A generator stored per stable environment slot does not inherently depend on Rayon scheduling. A generator stored per executing OS worker can. The environment must specify stable slot/episode stream ownership, reserve evaluation seeds, and test identical results across thread/chunk configurations. A deterministic slot/counter scheme is a suitable implementation; the review's blanket claim about all per-worker PRNGs is too broad.

**Visibility and offscreen coordinates.** Negative or beyond-screen coordinates are valid, particularly for partly visible boxes. The strict non-clairvoyance rule conflicts with exposing newly spawned, entirely hidden entities. Before Milestone 2 freezes its observation contract, resolve this with conservative visibility/history rules that retain unclipped coordinates for admitted entities. Warning-announced geometry needs separate treatment. An AABB overlapping the screen does not guarantee identifiable pixels because of occlusion, palette, raster rounding, and camera movement. The review's proposed rendered-pixel test is therefore not a general observability oracle.

**Canonical coordinates.** The core's canonical projection samples physical pixels at `(world_x - camera_x, world_y - camera_y)` into output index `(world_x, world_y)`. It reverses camera translation while retaining zero padding where physical coverage is absent. The new `render_into` uses this projection. Rasterized auxiliary boxes therefore use canonical world coordinates; applying the camera offset again would misalign them. This qualifies the review's statement that shake shifts the canonical picture by two pixels.

**Collision prediction.** The native collision pass precedes movement and uses strict inequalities. Slab time and constant-velocity features remain predictions, with pickup/list-order, anti-camping spawns, shrink changes, and moving geometry as exceptions. Point-size player boxes during shrink and degenerate rectangle extents need explicit signed-gap tests. Do not label the geometric feature an unconditional exact death oracle.

For each axis, use `max(entity_min - player_max, player_min - entity_max)` as the signed gap. A shrunk player's pattern collision box is a point; this expression is negative when the point is strictly inside a rectangle. An overlap-length expression returns zero in that case and would misclassify it. Newly created kamikaze explosions also begin at size zero and can still collide with a nonzero player box. Do not apply a blanket zero-area filter to enemy/explosion records when rejecting invisible scheduling rectangles.

**Motion features.** `vx * game_speed * freeze_rate * enemy.speed` estimates translation from the current state, including for powerups. Growing enemy centers also move by half their size change; expanding explosions shift their top-left to keep their center approximately fixed under fixed-point rounding. Stored velocity is the velocity used in that entity's position update, but score changes later in the enemy loop can alter the final global speed. Label analytic displacement as a current kinematic estimate, rather than claiming it reproduces every entity's exact previous-frame center displacement. Any exact historical-delta instrumentation needs stable identity and lifecycle tests.

**Catalog geometry.** At `d7ad951`, pattern 17 is a type-0 16×16 rectangle with a Wait target; the claimed special smooth resizing is not implemented there. The final catalog's zero-area rectangle is the offscreen control rectangle in pattern 23. Do not invent movement/growth from the specification's example. A synthetic width-zero rectangle can still satisfy the engine's literal inequalities because its collision upper bound is `x + width - 1`; do not sort, take absolute values, or silently treat inverted bounds as an exact collision oracle. Catalog assumptions need tests, and time-to-contact zero remains distinct from strict current overlap.

**Additional evaluation proposals.** The review's bootstrap gate and 1,000 evaluation episodes per difficulty are proposed acceptance details, not text supplied by the user. Final sample counts, confidence calculation, and score/survival margins will be fixed from Milestone 0 evidence and resource measurements before teacher evaluation. Reserved evaluation seeds must not be used for optimization or adaptive training-label collection.

The current Milestone 0/1 agents remain scoped to their original implementation tasks. These decisions are inputs to their parent review and subsequent Milestone 2 work; a completed audit does not mean every item is implemented or tested.

## M2 interface issues identified during design

- `render_into` on a dead state includes the Game Over overlay. Do not push that image into the four-frame history. Preserve actual terminal privileged features with an explicit invalid pixel/state-pair marker; terminated transitions do not bootstrap. Alive truncated observations retain valid current pixels and do bootstrap. Explicit slot resets refill all four frames and never mix a new episode's image with a terminal state's features.
- Raw rectangle warning arrays do not by themselves identify currently drawn warnings. Add a render-derived current-warning accessor or predicate rather than exposing its underlying timer as a feature. Hidden-state invariance tests must hold current visual phenotype and observed history fixed; changing a timer across a threshold that changes visible warnings can legitimately change auxiliary targets.
- Enemy vector indices are not stable identities across removals. Required motion/growth features need observed raw-frame kinematics or reliable identity instrumentation without altering canonical gameplay or snapshot semantics. Unknown zero values are appropriate for new/reset records when logged; they are not a substitute for implementing all growth features.
- Derive rectangle half-extents from the literal collision interval ending at `x + width - 1`. Keep this distinct from the inclusive visual footprint. Degenerate explosion points require explicit half-open patch assignment, including coordinates exactly on an 8-pixel patch boundary; a positive-area overlap calculation would erase them.

These are design requirements awaiting the reviewed vectorized-environment implementation, not claims about an existing M2 API.

## M2 contract review reconciliation

The read-only Opus contract review is retained in `learning/runs/v2-orchestration/m2_contract_opus_r1-result.json`. Revision 2 of the [environment contract](v2-environment-contract.md) adopts serial-only core metadata, wrapper-owned raw-frame geometry history, the exact scene warning predicate, type-correct powerup extents, deterministic overflow ties, explicit reset/poison ownership, raw-gameplay caps, and fixed-point raster arithmetic. Identity and history-valid metadata remain outside neural inputs and snapshot wire data.

Parent source checks qualify three proposals. First, the initial admission rule uses current conservative renderer footprints at observation boundaries; indefinite sticky offscreen tracking is deferred because it can exceed short visual history. Second, unknown or flat sub-two charge history yields no future-lethal forecast; missing history is not evidence of charging. Third, zero-size explosions draw a body pixel and a shadow pixel, and negative enemy visual size is clamped to zero by `render_game` before drawing. A secondary review's proposed reversed negative enemy footprint missed this clamp. Rectangle visual endpoints can be normalized by rasterization; collision endpoints cannot. Warning admission and targets include both the rounded main segment and its `y+1` shadow.

No core or wrapper implementation has yet been accepted for these interfaces. Existing Milestone 1 tests must run again after core changes; old counts are not new validation.
